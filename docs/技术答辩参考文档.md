# 技术答辩参考文档 · 充电运营大数据平台

> 用途：答辩 / 演示前通读，讲清「用了什么技术、数据怎么走、算法什么原理、为什么快」。
> 配合：《后续扩充计划-BigDemo增强路线图.md》第 0 节（环境交接）+《Hadoop环境操作与重启恢复手册》。
> 诚实口径：**业务数据为仿真生成；机器学习为可解释白盒/规则模型（非深度学习训练）**——这是设计决策，答辩主动讲出来反而是加分项。

## 一、系统总体架构（四层 + 数据闭环）

| 层级 | 名称 | 核心能力 | 落地形态 |
|---|---|---|---|
| 第一层 | 用户服务层 | 智能找站、推荐、预约排队、充电结算 | 用户端（Qt QML 桌面程序，模拟手机） |
| 第二层 | 设备管理层 | 设备监控、健康度、故障处置 | 管理端（Qt Widgets 宽屏后台） |
| 第三层 | 智能决策层 | 负荷预测、需求预测、调度、风控 | 机器学习引擎（C++ 白盒 + Python 复刻上大屏） |
| 第四层 | 运营分析层 | 运营驾驶舱、营收、碳排、what-if 仿真 | 大数据可视化大屏（Web + ECharts） |

**数据闭环（演示主线）**：
用户充电行为产生订单/设备数据 → 数据进入大数据链路（Hive）→ Spark 预聚合 → 大屏展示 → 预测/调度建议反过来指导运营 → 运营动作产生新数据。

**跨端联动**：用户端、管理端通过 WebSocket/JSON 连 C++ 服务进程（QWebSocketServer），统一读写 SQLite；大屏通过 HTTP 连 Python 网关读 Hive 聚合结果。

## 三、数据链路（重点讲这个）

```
┌─────────────── SQLite 业务库 charge.db（31 表）───────────────┐
│  make_seed.py 生成仿真数据（用户/站点/桩/订单/告警/评价…）      │
└───────────────────────────┬───────────────────────────────────┘
                            │ _export_hive.py（一键导出）
                            ▼
┌─────────────── hive_sync/（每表 .sql 建表 + .tsv 数据）────────┐
│  TSV 制表符分隔、空值 \N、全列 STRING、30 张表                 │
└───────────────────────────┬───────────────────────────────────┘
                            │ load_hive.sh（beeline LOAD DATA LOCAL INPATH）
                            ▼
┌─────────────── Hive 数据仓库 chargestation（30 表）────────────┐
│  charging_order / charging_measure / charger / station / review … │
└───────────────────────────┬───────────────────────────────────┘
                            │ dash_engine.py（SparkSession 单会话预聚合）
                            ▼
┌─────────────── dash_cache.json（预聚合缓存，秒回核心）──────────┐
│  status / trend / rank / stations / alarm / 筛选维度(region_*) │
│  / ML 区段(demand_heat / health / review / load_trend…)        │
└───────────────────────────┬───────────────────────────────────┘
                            │ 网关 app.py 读缓存组装 JSON
                            ▼
┌─────────────── 大屏（ECharts 渲染 20 个面板）──────────────────┐
│  /api/snapshot 业务快照 · /api/ml 机器学习面板 · /api/forecast  │
└───────────────────────────────────────────────────────────────┘
```

**关键点**：Hive 只承担"存 + 批量算"，网关不在请求热路径上逐条跑 Spark（每条起 JVM 15~30s，10 条就几分钟）——而是**用 Spark 一次性把聚合算好落盘（dash_cache.json），网关只做内存组装，秒回**。这就是大屏快的根本原因。

## 四、大屏网关（app.py）路由

纯标准库 `http.server`，零依赖，一个文件两个职责：静态托管 + 数据 API。

| 路由 | 说明 |
|---|---|
| `/` → index.html | 大屏（`?mode=live` 真实数据 / 默认实时） |
| `/hadoop` | Hive/Spark SQL 查询演示页（返回大屏导航） |
| `/admin` | 开发者模式（数据管理台） |
| `GET /api/snapshot` | 大屏业务快照；参数 `region / station_id / date` 筛选秒回 |
| `GET /api/forecast` | PME 24h 负荷预测 |
| `GET /api/ml` | 机器学习面板聚合数据（一次返回 9 项） |
| `POST /api/spark` | 执行 spark-sql（/hadoop 页与弹窗用） |
| `POST /api/hive` | 执行 beeline Hive SQL |
| `/api/admin/*` | 表行数、DESCRIBE、INSERT、文件导入、清空、重建缓存 |

**mock / live 双模式**：`?mode=live` 走网关真实数据；默认实时；右上角「●实时 / ○演示」开关，选择存 localStorage，切页不丢。

## 五、性能优化三板斧（答辩必讲）

1. **预聚合缓存**：dash_engine 单次 Spark 会话把所有面板需要的聚合一次算完 → `dash_cache.json`，大屏秒回。
2. **筛选预聚合**：把「区域维度 + 站点维度」统计在重建时用 GROUP BY 一次算好（region_* / station_* 区段），网关收到筛选参数只做**内存行选择 + 聚合**——零 Spark、秒回，不再是摆设。
3. **三级降级**：缓存缺失 → spark-sql 单会话兜底（起一次 JVM 算全部，~30~60s，结果缓存 10 分钟）→ beeline 最后兜底；前端另有 mock 数据兜底，**任何环节挂了界面都不白屏**。

历史 Bug 修复（体现工程能力）：/api/snapshot 卡顿（改缓存）、收入图空白（ECharts 双 Y 轴两次 setOption 崩溃 → 改单次）、筛选慢（预聚合方案）。

## 六、机器学习算法原理（白盒、可解释）

> 设计原则（对齐 `ML-Algorithm-Docs.md`）：可解释优先、零外部依赖、可降级。C++ 引擎（Qt 桌面）为参考实现，大屏用 **Python/JS 按公式复刻**，数据由 Spark 预聚合。

### 1. PME 负荷预测（周期性移动平均外推）
- 把近 7 天负荷按「小时」分桶取均值（早晚双峰模板），加温和增长系数 + 乘性噪声外推未来 24h。
- 置信区间：`预测 × (1 ± 1.645σ)`（90% 区间）。
- 大屏呈现：历史实际线 + 未来预测虚线 + 置信区间阴影带。

### 2. 需求热力（DemandForecast）
- 按「星期 × 小时 × 区域」聚合有效订单数 → 7×24 热力图（横轴小时、纵轴星期）。
- 激增检测：`Δ = (D − 该区域该小时均值) / 均值`，Δ > 50% 标记「需求激增」并列出 TOP 窗口，用于提示增配快充桩。

### 3. 设备健康度（HealthAssessment）
- 满分 100 扣分制：温度 >50℃ 扣 2×(T−50)；通信异常扣 15；按 `健康分` 字段 + 温度/通信修正得到最终分。
- 故障风险 `R = (100−H)/100 × 0.8`，按阈值分低/中/高；高风险桩在列表置顶标红。

### 4. What-If 决策推演（纯前端实时算）
- 滑条输入：增配桩数 / 电价调整 / 客流变化。
- 公式：日订单 `N' = N₀×(1+客流)×(1−0.2×电价差)`；日营收 `= N'×(客单价+电价差×单均电量)`；高峰利用率 `= 高峰需求×(1+客流)/(桩数+增桩)`；排队等待按桩数反比。
- 演示效果：拖滑条，4 个指标实时变化——"加 5 台桩、降 0.2 元 → 营收涨 XX"。

### 5. 评价标签分析（ReviewTag）
- Hive 的 review 表 `tags` 是 JSON 字符串，Python 侧 `json.loads` 统计标签频次 → TOP5 横向条形。
- 五维评分（速度/设备/停车/卫生/服务）取均值 → 雷达图。

### 6. 智能调度建议（Dispatch 规则引擎）
- 三条规则：空闲率 <20% → A4 运营告警 + A1 提升附近站推荐；排队 >5 → A3 积分×2 + A2 立减券引流；高峰预测利用率 >90% → 提前调配电力。无触发显示"运行平稳"。

### 7. 充电效率分析 / 近7日负荷走势
- 效率：快充 vs 慢充 平均时长/电量/订单量对比柱状图。
- 走势：7 天每天一条 24h 负荷曲线叠加（浅灰）+ 今日红色高亮线 + 7 日均线虚线（股票分时风格）。

### 其余引擎（未上屏，可口头带过）
推荐评分（距离/价格/空闲/健康加权）、等待时间预估（排队×平均剩余）、智能风控（高频预约取消/短时刷单）、AI 运营助手（模板问答）。

## 七、Hadoop / Spark 大数据分析（演示话术）

- **HDFS** 存数据文件，**YARN** 做资源调度，**Hive** 提供 SQL 化数据仓库（30 表），**Spark** 做内存计算。
- `/hadoop` 页 + 大屏「大数据分析」弹窗：8 维 SPARK-SQL 实时分析（区域分布 / 桩型 / 订单状态 / 分时电量 / 站点 TOP / 用户等级 / 电价档位收入 / 峰谷对比），现场敲 SQL 就能跑，演示"大数据引擎"。
- 对比话术：Hive 的 count(*) 是完整 MR 作业（小表也要十几秒），Spark 内存计算快得多 → 所以大屏聚合走 Spark。

## 八、开发者模式（/admin，应对"老师现场给数据"）

- 表一览：一次 Spark 会话批量统计 30 表行数（秒回，缓存缺失自动降级）。
- 文件导入：TSV 直接 `LOAD DATA LOCAL INPATH`（最快）；CSV 走临时表转换再 `INSERT SELECT`；自动校验列数。
- 手动添加：`DESCRIBE` 动态生成表单 → 按列名 `INSERT INTO ... VALUES`。
- 清空表、一键**重建大屏缓存**（重跑 dash_engine.py，30~60s 后大屏自动生效）。
- 场景：老师现场给一份 CSV → 传到 /admin → 导入 → 重建缓存 → 大屏秒变。

## 十、答辩 Q&A 预演

**Q1：数据是真实的吗？**
A：业务数据是**仿真生成**的（固定随机种子、可复现，且生成逻辑就是按充电业务规律建模：早晚双峰、工作日/周末差异）。真实性和可控性我们选可控——演示时能稳定复现任意场景。真实接入只需把导出脚本指向生产库。

**Q2：机器学习是训练出来的吗？**
A：不是深度学习，是**可解释白盒模型**（统计 + 规则）。这是有意的设计：充电运营场景要求结果可追溯、可复算——预测值能讲清"为什么这么预测"。比如 PME 就是"过去同期均值 × 增长 × 置信区间"，每个数都能解释。

**Q3：大屏为什么快？**
A：查询不在请求时算，而是 Spark 预聚合落盘（dash_cache.json），网关只做内存组装；筛选也是预聚合维度，运行时零 Spark。

**Q4：Hive 和 MySQL 区别？为什么用 Hive？**
A：MySQL 是 OLTP（事务处理），count(*) 走索引统计毫秒级；Hive 是 OLAP（分析），一个 count(*) 就是一个 MapReduce 作业，固定开销十几秒——但它能横向扩展、处理海量数据（TB 级），且 SQL 化门槛低。我们要展示的是"大数据处理能力"，所以数据入仓 Hive。

**Q5：怎么证明处理过大数据？**
A：charging_measure 等大表走 Spark 预聚合；/hadoop 页可直接对海量表跑 SPARK-SQL 多维分析。需要时可以现场用造数脚本灌 100 万行再跑分析。

**Q6：筛选联动为什么秒回？**
A：区域/站点维度的统计在缓存重建时用 GROUP BY 一次性算好存进 dash_cache，网关收到筛选参数只做行筛选 + 求和，纯内存，所以秒回。

**Q7：架构上还有什么可扩展？**
A：网关可换 Flask/FastAPI；预聚合可上调度（定时重建）；Spark 可改常驻会话做实时；数据源可从 SQLite 换成 MySQL/PG。演示当前版本用最简实现跑通全链路。

## 十二、常见翻车点与兜底

- 缓存旧/被删 → 大屏回退 mock（不白屏）；重建缓存即恢复。
- Spark 首次启动 30s → 演示前先预热（跑一次查询）。
- 筛选需新版 dash_cache（含 region_*/station_*）→ 传完文件务必重建缓存。
- `vendor/echarts.min.js` 是本地产物，**不要上传覆盖**服务器版本。
