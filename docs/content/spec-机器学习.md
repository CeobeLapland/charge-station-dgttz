# spec-机器学习

定位：贯穿各端的算法能力层，不独立面向用户。数据源为 `charging_measure`、`charger.health_score`、订单与用户行为，并引入天气、节假日等外部维度。落地原则：主方案为 **C++ 内规则 + 仿真数据**，Python FastAPI 仅作可选加分端点（见 `AGENTS.md` 禁忌）。

## 能力清单与消费方

| 能力 | 优先级 | 模型产出 | 主要消费方 |
| ---- | ---- | -------- | ---------- |
| 充电负荷智能预测 | 基础 | 负荷/空闲桩/高峰时段 | 用户端避峰、大屏曲线、运营值守 |

## 功能规格

### 充电负荷智能预测【基础】

- 输入：各站/各桩历史充电时段、充电时长、充电量、出行时段、天气、节假日。
- 输出：未来 1/6/24 小时各站充电负荷、空闲桩数量、高峰充电时段。
- 消费：用户端优先推荐低拥堵高空闲站；运营端负荷预警。
- 实现（规则+仿真，必做）：
  1. 造数据：服务端模拟线程按 `负荷 = 基线 + 早晚双峰正弦 + 随机噪声` 生成历史负荷，让曲线天然有峰谷规律。
  2. 做预测：取"过去同一天曲线 × 增长系数 + 噪声"作为未来 24 小时预测，或对最近 N 点做线性/移动平均外推。
  3. 做展示：大屏实线=实际、虚线=预测、阴影=置信区间（ECharts `areaStyle`）。
- 验收：大屏出现未来 1/6/24h 预测曲线且贴合历史；用户端避峰提示引用的预测可追溯。

### 天气维度（跨能力输入）【增强】

- 输入：天气状况（可模拟：晴 / 雨 / 高温 / 极端天气，无需真实天气 API，由服务端定时器按概率或手动设置）。
- 输出与影响：降雨后需求偏移（如"晚高峰充电需求下降 11%、室内站需求上升 18%"）；高温时充电时长可能延长、设备温度风险升高；极端天气给站点风险提示并影响推荐排序。
- 消费链：天气 → 负荷预测偏移 → 用户端天气推荐 → 大屏预测曲线 → 管理端告警 → 优惠策略（如雨天给室内站发券）。
- 实现：在负荷生成与预测公式中加入天气修正系数（晴天系数 1.0，雨天室内站 ×1.18/室外 ×0.89 等），`[待定]` 系数由实现定稿。
- 验收：切换模拟天气后，预测曲线与用户端推荐排序发生可观察变化。

### 故障预测【增强】

- 输入：每桩历史异常次数、功率波动、温度趋势。
- 输出：未来 24 小时故障风险概率（如"A-023 未来 24 小时故障风险 78%"），管理端按风险排序。
- 实现：健康度规则公式 `100 − 温度惩罚 − 通信惩罚 − 功率波动惩罚 − 异常次数`；故障风险 = `(100 − 健康度) × 系数 + 噪声`，clip 到 0–100。
- 验收：高风险桩排序可复算，管理端展示风险分。

### 用户需求预测【增强】

- 输入：按时段与区域聚合的历史充电需求。
- 输出：需求激增的时间窗与地理位置（如"18:00–20:00 商业区需求激增"），资源建议（"推荐在商业区增加快充桩 12 台"）。
- 实现：按"星期几 × 小时"聚合历史订单量，得到 24×7 需求分布。
- 验收：大屏热力图/柱状图展示需求分布，结论可复算。

### 智能调度【增强】

- 闭环：预测（17:00 某站拥堵）→ 决策（部分用户推荐至他站 / 提高该站激励）→ 执行（改推荐排序与积分倍率）→ 反馈（观察负荷与排队变化回写模型）。
- 验收：模拟拥堵场景后，用户端推荐排序或积分倍率发生可观察变化。

### 智能推荐引擎【增强】

- 输入：负荷预测提供的空闲桩/拥堵预测、分时电价、健康度。
- 输出：候选站评分与"最快/最省钱/综合最优"三类结果。
- 评分权重 `[待定]`（建议初值：距离 0.3 / 价格 0.3 / 等待 0.2 / 健康度 0.2）。
- 消费：`spec-用户端` 智能推荐、一键找桩、避峰推荐共用此排序逻辑。
- 验收：三类标签对应不同排序。

### 智能风控【增强】

- 输入：用户行为（高频预约又取消等）。
- 输出：风险评分 0–100 与等级（低/中/高），处置建议（限制预约/冻结/忽略）。
- 实现：基础版阈值规则（建议初值：24 小时预约 ≥ 10 次且取消率 ≥ 60% 触发）。
- 验收：构造异常行为后用户被识别并标注。

### what-if 决策仿真【增强】

- 输入：假设条件（加/减桩、降电价、故障规模、客流变化）。
- 输出：平均等待时间、峰值利用率、预计日订单、预计日营收的对照推演。
- 实现：与需求模型共用推演逻辑。
- 验收：任一假设给出四项指标影响。

### AI 运营助手【增强】

- 输入：自然语言问题 + 数据库经营/设备数据 + 负荷/故障预测结果。
- 输出：可追溯数据来源的回答。
- 验收：回答中的每条结论能对应到数据记录或预测输出。

### 等待时间预估【增强】

- 输入：当前队列长度、历史同周期平均单桩充电时长、负荷预测。
- 输出：当前预计等待 N 分钟，以及"现在去 / 10 分钟后 / 20 分钟后"三档等待时间，附"建议现在前往/稍后前往"结论。
- 实现：`等待 ≈ 排队人数 × 历史同期平均剩余充电时长`；未来窗口用负荷预测外推队列变化。纯规则可实现。
- 消费：`spec-用户端`「预计等待时间」。
- 验收：排队人数变化后等待时间随之更新，三档时间与建议结论可复算。

### 评价标签分析【增强】

- 输入：`review` 表标签、分维度评分、有用数。
- 输出：标签频次与环比（如"XX 站排队严重标签 30 天增长 42%"）、用户反馈问题 TOP5 占比、各站分维度评分。
- 实现：SQL 聚合 + 标签计数；环比 =（本期 − 上期）/ 上期。
- 消费：`spec-大屏`「评价与反馈分析」、管理端工单/告警。
- 验收：某站"排队严重"等标签数据可复算，TOP5 占比合计 100%。

## 评估与兜底

- 准确度定义：负荷预测以"预测与实际平均偏差率"衡量（建议初值：小时级偏差率 ≤ 15% 视为可用）；故障预测以"高风险设备实际发生故障命中比例"衡量。阈值 `[待定]`。
- 评估方式：历史数据留出集回测，训练/验证按时间顺序切分。
- 兜底机制：模型不可用或质量不达标时回退规则策略——推荐退化为"距离近 + 空闲多"排序，避峰退化为固定分时电价提示。核心流程不因模型故障中断。

## 技术落地选择

只选一种，别都做：

| 方案 | 做法 | 说明 |
| ---- | ---- | ---- |
| A（推荐） | 全部 C++ 内实现：公式 + 随机数 | 零跨语言、编译即跑；答辩说法最弱但稳定 |
| B | Python FastAPI 提供 1–2 个 `/predict` 接口返回 JSON | 视频可拍 Python + sklearn；需装依赖 |
| C | 大屏 JS 端移动平均外推 | 最省事但服务端拿不到，难跨端联动 |

若组内有会 Python 的同学，可在 A 之外加最小 FastAPI 端点（`sklearn.LinearRegression` 或 `numpy.polyfit`）返回预测 JSON，专门用于"C++ 拿到 Python 预测结果渲染到曲线"的镜头。
