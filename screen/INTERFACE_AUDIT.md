# Web 大屏接口核对与联调清单

更新时间：2026-09-04

本文记录 `screen/` 当前前端实现与 `server/` 当前服务端实现的实际对接状态。正式消息名称和公共信封仍以 `docs/content/spec-协议.md` 为准；大屏完整字段说明见 `screen/API_CONTRACT.md`。

## 1. 当前结论

当前已经具备可用的 WebSocket 全量快照链路：浏览器连接服务端后会自动请求 `screen.snapshot`，服务端返回的字段能够被页面直接消费并渲染。

当前还不是完整的持续实时大屏。服务端只在管理员执行电桩重启或暂停操作时广播 `push.charger_status`，尚未持续广播告警、订单事件、负荷和预测数据。页面也没有固定周期轮询快照，因此没有推送时，数据库发生变化不会立刻显示在网页上。

## 2. 连接约定

| 项目 | 当前值 |
| --- | --- |
| 传输协议 | WebSocket |
| 默认地址 | `ws://127.0.0.1:9000` |
| 消息编码 | UTF-8 JSON 文本 |
| 大屏鉴权 | 无需登录，只读 |
| 心跳 | 浏览器每 15 秒发送一次 `system.ping` |
| 失败处理 | 连续 3 次未收到 pong 后断开并指数退避重连 |
| 初始同步 | 首次连接和重连成功后自动请求快照 |
| 数据过期 | 60 秒没有业务数据更新时显示“数据已过期” |
| 前端配置 | `screen/js/config.js` |

`127.0.0.1` 指浏览器所在的电脑。如果浏览器与服务端不在同一台电脑，必须把地址改成服务端局域网 IP，例如 `ws://192.168.31.130:9000`，同时确认服务端防火墙允许 TCP 9000 端口。

## 3. 统一消息信封

请求：

```json
{
  "type": "screen.snapshot",
  "seq": 1,
  "payload": {}
}
```

响应：

```json
{
  "type": "screen.snapshot_resp",
  "seq": 1,
  "code": 0,
  "message": "ok",
  "payload": {}
}
```

主动推送：

```json
{
  "type": "push.alarm",
  "payload": {}
}
```

要求：响应必须回填请求的 `seq`；成功响应 `code` 必须为 `0`；主动推送不带 `seq`。

## 4. 接口实现状态

| 消息 | 方向 | 前端 | 服务端 | 当前状态 |
| --- | --- | --- | --- | --- |
| `screen.snapshot` | 大屏 → 服务端 | 已发送 | 已处理 | 可联调 |
| `screen.snapshot_resp` | 服务端 → 大屏 | 已校验并渲染 | 已返回 | 可联调 |
| `system.ping` | 大屏 → 服务端 | 已实现 | 已处理 | 可联调 |
| `system.pong` | 服务端 → 大屏 | 已处理 | 已返回完整信封 | 可联调 |
| `push.charger_status` | 服务端 → 大屏 | 已处理 | 仅管理员操作时发送 | 部分可用 |
| `push.alarm` | 服务端 → 大屏 | 已处理 | 未发送 | 待服务端实现 |
| `push.order_event` | 服务端 → 大屏 | 已处理 | 未发送 | 待服务端实现 |
| `push.forecast` | 服务端 → 大屏 | 已处理 | 未发送 | 待机器学习/服务端实现 |
| `ml.forecast` | 大屏 → 服务端 | 当前页面未主动请求 | 固定返回 `5001` | 预测模块未接入 |

## 5. 快照字段核对

服务端当前返回以下 `screen.snapshot_resp.payload`：

| 字段 | 页面用途 | 服务端口径 | 核对结果 |
| --- | --- | --- | --- |
| `metrics.today_revenue` | 今日营收 | 今日已结算订单 `pay_amount` 合计 | 一致 |
| `metrics.today_orders` | 今日订单 | 今日创建的全部订单，不区分最终状态 | 已明确 |
| `metrics.charging_count` | 当前充电 | `charger.status = charging` 数量 | 一致 |
| `metrics.online_rate` | 在线率 | 非 `offline/fault` 桩数 ÷ 总桩数 × 100 | 返回 0–100，一致 |
| `metrics.revenue_change_pct` | 营收同比昨日同期 | 昨日相同时刻为截止点 | 一致 |
| `metrics.orders_change_pct` | 订单同比昨日同期 | 昨日相同时刻为截止点 | 一致 |
| `stations[]` | 站点分布 | ID、名称、经纬度、负载、空闲数、总数、今日营收 | 字段一致 |
| `load_series.actual[]` | 实际负荷 | 近 24 小时 `charging_measure.power_kw` 汇总 | 字段一致 |
| `load_series.forecast[]` | 预测负荷 | 当前固定为空数组 | 待预测模块 |
| `utilization_rank[]` | 利用率排名 | 今日订单时长 ÷ 今日已过时间容量 | 字段一致 |
| `alarms[]` | 告警列表 | 最近 20 条告警 | 基本一致 |
| `user_growth[]` | 用户增长 | 最近 7 天，缺失日期补 0 | 一致 |
| `energy_by_price_level` | 峰平谷电量 | 最近 7 天已结算订单电量 | 字段一致；页面应理解为近 7 日 |
| `events[]` | 初始事件列表 | 今日订单创建、开始和结算事件 | 一致，手机号已脱敏 |

注意：站点级告警的 `charger_id` 按契约应明确返回 JSON `null`。服务端当前使用默认 `QJsonValue()`，可能导致字段被省略，建议服务端改为显式空值。

## 6. 页面当前刷新机制

### 自动发生的更新

1. 使用 live 模式打开网页后，自动建立 WebSocket 连接。
2. 连接成功后自动请求一次完整快照。
3. 断线后自动重连，重连成功后重新请求完整快照。
4. 收到 `push.alarm`、`push.order_event` 或 `push.forecast` 时局部更新页面。
5. 收到 `push.charger_status` 时更新事件流；如果消息没有携带聚合指标，前端最多每 2 秒自动重拉一次快照。

### 当前不会自动发生的更新

- 服务端数据库变化本身不会通知浏览器。
- 页面没有按固定时间周期请求 `screen.snapshot`。
- 当前服务端没有发送 `push.alarm`、`push.order_event`、`push.forecast`。
- 实际负荷曲线不会仅因为数据库新增 `charging_measure` 就自动滚动。

因此，当前页面无需点击按钮手动更新，但只有在“首次连接、自动重连或收到电桩状态推送”时会自动刷新完整数据。其他数据库变化若没有对应推送，需要刷新浏览器页面才能重新拉取，或者补充服务端推送/前端定时快照机制。

## 7. 完成连接需要做的工作

### 7.1 启动服务端

首次运行需要生成数据库并编译服务端：

```bash
cd server/sql
python3 make_seed.py

cd ..
cmake -B build
cmake --build build

cd build
./charge_server
```

服务端出现“监听端口 9000”和“等待各端连接”后，网络端才准备完成。

### 7.2 启动网页 live 模式

在 `screen/` 目录启动静态文件服务，然后访问带 `mode=live` 的地址。例如：

```bash
cd screen
python3 -m http.server 8080
```

浏览器访问：

```text
http://127.0.0.1:8080/index.html?mode=live
```

直接打开 `index.html` 或不带 `mode=live` 时，页面使用 mock 演示数据，不会连接服务端。

### 7.3 跨机器连接

如果网页和服务端不在同一台电脑：

1. 将 `screen/js/config.js` 的 `websocketUrl` 改为服务端实际 IP。
2. 服务端当前监听 `QHostAddress::Any`，无需再改监听地址。
3. 放行服务端 TCP 9000 端口。
4. 确认浏览器电脑能访问服务端 IP。
5. 如果网页最终通过 HTTPS 发布，WebSocket 也必须升级为 `wss://`，否则浏览器会阻止混合内容。

### 7.4 服务端还需补齐

要实现完整实时大屏，服务端负责人还需要：

1. 在订单创建、开始、完成和结算后发送结构化 `push.order_event`。
2. 新告警入库后立即发送 `push.alarm`。
3. 设备状态或采集数据变化时发送 `push.charger_status`，最好携带 `station_id` 和最新 `metrics`。
4. 实际负荷发生变化时提供推送，或约定前端定时重拉快照。
5. 机器学习产出预测后发送 `push.forecast`，包含时间、预测值和上下置信区间。
6. 将推送限定到合适客户端；当前 `broadcast()` 会向所有 WebSocket 连接广播。
7. 将站点级告警的 `charger_id` 显式序列化为 JSON `null`。

### 7.5 联调验收

- 页面显示“实时连接”，且服务端日志出现 `screen.snapshot`。
- 四个指标与数据库查询结果一致。
- 管理端改变电桩状态后，大屏在 2 秒左右更新指标和事件。
- 新增告警后，大屏和管理端同时出现相同 `alarm.id`。
- 订单开始或结算后，事件流无需刷新浏览器即可出现新记录。
- 服务端停止后页面显示重连状态；恢复服务端后自动重连并重新拉取快照。
- 60 秒没有业务数据时页面显示“数据已过期”。
- 预测不可用时保留实际负荷，不生成虚假预测数据。

## 8. 建议的实时方案

优先采用“全量快照 + 业务增量推送”：连接和重连时拉取快照，正常运行时由服务端按业务事件推送。这能避免高频全量查询，也能保证断线恢复后的数据完整性。

在服务端推送尚未全部完成的过渡阶段，可以在前端每 15–30 秒请求一次快照，但这只能作为临时方案。正式版本应由服务端事件推送驱动，并对高频负荷数据设置固定时间窗口和推送频率。
